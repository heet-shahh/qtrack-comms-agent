qTrack · Patient Communication · POC Plan

Goal-Directed Patient Communication Agent

2026-07-20 Status: POC design LCS + IPN Track A + Track B

This POC proves one idea: a single state-machine engine can turn a clinical trigger into a tracked conversation that either reaches its objective on its own, or hands off cleanly to a navigator. We start on Slack because it gives us the patient side and the navigator side in one tool with no telephony overhead. The channel is a swappable adapter; the brain we build now is what carries straight over to voice later.

01 The Thesis

The adherence gap is not a copywriting problem. It is that a trigger (a no-show, an overdue follow-up, a filed finding) never reliably becomes a tracked action with an owner and a goal. So the thing worth building is not "a bot that texts patients." It is an engine that, for each condition, knows: what it is trying to achieve, what it will say to get there, how it reads the reply, and what happens next whether it succeeds or fails.

Everything in this POC is organized around one architectural bet: the channel is a detail, the brain is the product. Today the brain speaks over Slack. Tomorrow the exact same brain speaks over a voice line. Nothing about the trigger logic, the state machine, the goal definitions, or the escalation flow changes when we swap the mouth.

What "done" means for the POC
A clinical condition on a seeded patient fires a trigger, the agent opens a Slack conversation with a stated goal (for example, capture a follow-up appointment date), it interprets the reply, it either records success and schedules the next task or escalates an off-script reply to a navigator, and every step of that is written to a durable, per-patient, replayable log.

02 Two Nouns, One Verb

The entire model is small enough to hold in your head. There are two data objects and one function that does all the work.

Playbook (the condition)

A versioned config object, one per condition. It is the "state machine definition." It never runs; it describes how a task of this type behaves. This is where a clinical or ops person, not an engineer, eventually edits behaviour.

FieldMeaning
triggerThe condition that mints a task: an event, or a derived "overdue by N days" scan predicate.
automation_tierautomatic or assisted. Decided by interaction type, not by importance.
goalThe achievable outcome the agent is chasing, for example capture a date, elicit interest, confirm attendance.
expected_outcomes[]The closed set of structured replies that count as "matched," for example confirmed, reschedule, declined.
barrier_signals[]Reply patterns that force immediate escalation even inside a matched reply (cost, fear, "why do I need this").
scriptThe prompt or template the LLM uses to compose each turn, plus the acknowledge-and-handoff script for fallout.
transitionsState to state rules: on this outcome, go to that state.
retry_policyMax attempts, wait interval, and the channel-escalation ladder (attempt 1 preferred channel, attempt 2 a different one).
next_taskWhat to spawn on success, for example on date captured, create a pre-scan reminder at T-48h.

Task (the running instance)

One task is one playbook running for one patient. It is the state machine instance. It carries the live context, the current state, the attempt count, and the outcome. It is the object every log row points back to. Its field set follows the PRD's Patient Communication Task (see section 08).

advance(task, event)

The one verb. The executor calls it whenever something happens to a task: a timer fires, or a reply arrives. It looks up the task's playbook, decides the next state, and along the way invokes the LLM brain (to compose or to interpret) and the channel adapter (to send). Every call writes a row to the event log. That is the whole runtime.

Why this shape
Adding a sixth condition later is writing one more Playbook config, not touching the engine. Swapping Slack for voice is writing one more adapter, not touching the playbooks. The state machine is the part that stays constant, so it is the part we invest in now.

03 The Five Playbooks

Five conditions for the POC, drawn straight from the build-spec: four automatic (binary or logistical interactions) and one assisted (an open clinical conversation). Each is a state machine with an explicit goal and an explicit next step.

#ConditionTierAgent's goalSuccess outcomeNext task on success
1LCS eligibility outreach auto Elicit interest in a free annual scan interested Enrollment / schedule-SDM task
2No-show / overdue chase (LCS + IPN) auto Capture a concrete (re)schedule date reschedule + date Pre-scan reminder at T-48h
3Pre-scan instructions / reminder auto Confirm attendance, acknowledge prep confirmed None (or post-scan follow-up)
4General appointment reminder auto Confirm attendance for any visit type confirmed None
5New finding (Lung-RADS 3/4A or IPN surveillance) assisted Prep a navigator, capture a structured call outcome capture_complete Continued-surveillance follow-up task
Note on 3 vs 4
Playbooks 3 and 4 are the same trigger-decision-delivery mechanics with a different content parameter (prep instructions vs generic confirmation). Build them as one capability with a content-type switch, not two code paths. They are listed separately only because that is how they were scoped.

The line that decides tier is not "how serious is this." It is can the useful reply be anticipated. "Does Tuesday at 2pm work" has a closed answer set, so it is automatic. "Is this serious, what does it mean" cannot be scripted, so it is assisted no matter how routine the underlying risk is. Playbook 5 is the only one where the answer is open, which is exactly why the agent's job there is prep and capture, not conversation.

04 Architecture

The external world sits on the left: EMR/RIS events and a nightly clock feed triggers in, and the patient and navigator both live on Slack. Everything in the container is what we build. The dashed region is the deliberate seam: the channel adapter is where Slack lives today and voice lives later, and nothing on its left cares which one is plugged in.

ComponentJob
Trigger engineTwo inputs: an event webhook (system-detected) and a nightly scan job (derived "overdue by N" predicates). Both mint tasks from a playbook.
Playbook registryThe five versioned configs. Loaded at task creation to stamp goal, transitions, retry policy onto the task.
State executorThe advance(task, event) loop. The only place state changes. Writes the event log on every transition.
LLM brainFour calls: compose a turn, interpret a reply against the goal, detect fallout, draft a summary. This is the part that becomes the voice agent's dialogue policy later.
Channel adapterAn interface with send() and an inbound reply callback. Slack implements it now; a voice implementation drops in later.
DataTask store (current state), event log (every transition), comm log (every message and reply, the raw thread).

05 The Conversation Loop

This is the heart of the POC, walked through on the overdue-chase example (playbook 2, goal: capture a reschedule date). Step through it and watch the active hop light up. The happy path is steps 1 to 6; step 7 is the branch that fires when the patient goes off-script.

→ → → → → →
Step 1 · Trigger fires

The nightly scan finds patient X's IPN follow-up CT is 30 days overdue with no future appointment. It mints a Task from playbook 2, stamping on the goal (capture a reschedule date), the expected outcomes, and the retry policy. State: QUEUED. First event-log row written.

Step 2 · Compose the turn

The executor calls the LLM brain with the playbook script plus context (first name, program, days overdue, the fact that a nodule is being tracked). The brain returns a short, single-question, opt-out-bearing message. State: IN_PROGRESS, attempt_count = 1.

Step 3 · Send over Slack

The Slack adapter DMs the patient (with a Reschedule / Confirm / Opt-out button set for the easy path, and free text allowed). The outbound message is written to the comm log as the raw thread. The channel used is recorded on the attempt.

Step 4 · Reply arrives

Patient replies "sure, how about next Monday afternoon?" Slack's event webhook delivers it to the response listener, which appends it to the same comm-log thread and calls advance(task, reply).

Step 5 · Interpret against the goal

The brain is asked one thing: does this reply satisfy the goal, and if so, extract the structured outcome. It returns {response_type: reschedule_requested, date: 2026-07-27} and no barrier signal. This is a match.

Step 6 · Close and chain

State moves to COMPLETED. The outcome_summary is written. The playbook's next_task rule spawns a fresh Task: a pre-scan reminder scheduled for T-48h before the captured date. The loop's whole point, a resolved objective plus the next objective queued, is achieved.

Step 7 · The other branch: off-script

Had the reply instead been "why do I even need this, I feel fine," interpret returns no matched outcome plus a fallout flag. The agent does not answer the clinical question. It runs the acknowledge-and-handoff script, sets state to ESCALATED, and creates a navigator task with the question text visible and an SLA attached (section 07).

1 / 7
Why the LLM interpret step matters
Buttons alone cannot cover a real patient reply, and a naive keyword match would misread "no, I can't afford this" as a plain decline. Asking the brain to score the reply against the goal, extract the structured outcome, and flag barriers in one pass is exactly the dialogue policy a voice agent needs. Building it now on text means the voice version inherits it.

06 Task Lifecycle

Every task, regardless of playbook, moves through the same generic states. What differs per playbook is the transition rules and the retry policy, not the state names. The automatic playbooks close on a matched reply; the assisted playbook (5) never closes on the call itself, only when the navigator fills the capture fields.

→ → → → →
State · CREATED

A trigger minted the task and stamped the playbook onto it. Nothing has been sent. This exists so the audit trail starts at birth, not at first contact.

State · QUEUED

Ready for the executor to pick up. For assisted tasks (playbook 5), queued means the navigator has been assigned and the pre-call brief is built and waiting in the queue.

State · IN_PROGRESS

A turn has gone out and we are waiting on a reply. attempt_count and channel_used are live here. For playbook 5 this is "the call is happening."

State · retry loop (still IN_PROGRESS)

No reply within the wait interval and attempts remain, so the executor re-sends on the next rung of the channel-escalation ladder (for example SMS then voice, or a second Slack nudge). This is a self-loop, not a new state.

State · COMPLETED

The goal was met: a matched outcome for automatic tasks, or the capture fields filled for the assisted one. The completion gate is what enforces this: an assisted task cannot reach completed until patient_understood, scheduled, questions_raised, distress_flag, and action_items are populated. next_task fires here.

State · ESCALATED (terminal for Track A)

Reached on max attempts, a barrier signal, or a fallout reply. The task leaves the automatic track and surfaces on the navigator queue with its full history and the triggering reply visible. A distress_flag on an assisted task routes here too, into a review queue.

1 / 6
The retry loop closes back
Step 4 loops back onto IN_PROGRESS rather than advancing. It only leaves the loop two ways: a reply arrives (to COMPLETED or ESCALATED) or the attempt budget runs out (to ESCALATED). That bound is what stops a task chasing a patient forever, and it is set per playbook in retry_policy.

07 Fallout & Escalation

The single most important safety behaviour: an automatic conversation must never guess at a clinical question, and it must never let a question silently drop. When the interpret step returns "no matched outcome" or trips a barrier signal, the agent runs the same three-move handoff every time.

→ → → →
Move 0 · Detect the fallout

The reply either matches no expected outcome, or matches one but carries barrier text ("no, I can't afford it"). Either way the brain flags it. V1 is deliberately simple: reply does not fit the closed answer set, so escalate. A richer classifier is a fast-follow once there is real conversation data.

Move 1 · Acknowledge, do not answer

No script exists for "why do I need this," so the agent does not improvise one. It acknowledges the question warmly and explicitly declines to answer it itself. This is the interaction-type gate doing its job in real time.

Move 2 · Name a specific human and a timeframe

"I'm going to have [Navigator], your care coordinator, call you back today." Named where possible via the patient's assigned navigator, falling back to the on-call role mapping. A named person and a "today" beats a vague "someone will follow up."

Move 3 · Confirm the part that did resolve

If the patient did confirm the appointment before asking the question, the agent still confirms that: "Thanks for confirming, we'll see you [date]." The handoff never makes the resolved part feel dropped. A call never ends mid-question.

Backend · Escalate with the question visible

State to ESCALATED; assigned_navigator resolves to the patient's navigator; the raw thread attaches via raw_log_ref; a structured escalation reason is written; the navigator queue card shows the actual question, not just "call back." An SLA (same business day) attaches so it cannot rot in the queue.

1 / 5

On Slack this is a real, demoable moment: the patient DM shows the graceful handoff, and a card appears in #navigator-queue the same instant with the flagged question and the transcript excerpt on it. That is Track A becoming Track B in front of you, which is the behaviour worth showing.

09 Stack & Why Slack

Deliberately boring, single-process, fast to stand up. Nothing here is load-bearing for the eventual product except the shape of the interfaces.

LayerChoiceWhy
RuntimePython + FastAPIOne service holds the webhook, the executor, and the adapters. Easy to reason about for a POC.
SchedulerAPSchedulerRuns the nightly scan and the retry-interval checks. No separate infra.
StoreSQLite (to Postgres later)The four tables above. Zero setup; migrate the day it needs concurrency.
ChannelSlack Bolt SDKPatient DMs + a #navigator-queue channel behind one adapter interface.
BrainAnthropic SDK (Claude)Compose, interpret, detect fallout, draft summaries. The dialogue policy that carries over to voice.

Why Slack is the right POC channel

Slack gives us both sides of the system in one tool with no telephony, no consent law, and no phone numbers. The patient is a DM thread; the navigator queue is a channel with Block Kit cards. Buttons cover the binary-logistics happy path, and free-text replies let us demo the LLM interpret step and the fallout handoff live. It is the fastest path to showing the actual behaviour that matters.

The alternative, and why we still start with Slack
WhatsApp or SMS via Twilio is one step more realistic (patients actually receive texts) and worth doing as the second adapter. But it adds sandbox setup, opt-in handling, and per-number friction that buys us nothing for proving the engine. Because both sit behind the same send() / reply-callback interface, moving from Slack to Twilio to voice is swapping an adapter, never touching a playbook. So we start on Slack precisely because the choice is reversible.

10 Build Plan & Deferred

Five milestones, each independently demoable. The order front-loads the risky part (one automatic playbook working end to end) and leaves breadth for last.

→ → → →
M0 · Skeleton and data model

FastAPI service, the four tables, the Slack adapter with send() and a reply webhook, and a seed script that loads a handful of synthetic patients with conditions. Prove a DM goes out and a reply lands in the comm log.

M1 · One automatic playbook, end to end

Playbook 2 (overdue chase) fully: nightly scan mints the task, the brain composes, Slack sends, a date reply is interpreted and captured, the task completes, and next_task spawns the pre-scan reminder. This milestone proves the whole thesis; everything after is expansion.

M2 · Retry ladder and fallout escalation

The retry loop with the channel-escalation ladder and a max-attempt bound, plus the three-move fallout handoff creating a card in #navigator-queue with the question visible and an SLA. This is the trust-critical behaviour.

M3 · The assisted playbook (5)

New-finding talk track: ownership fallback chain to know the task is even createable, a pre-call brief posted to the navigator, and the structured capture fields as the completion gate. V1 is talk-track plus manual capture, no recording. This is the Track B half.

M4 · Remaining playbooks and history views

Playbooks 1, 3, 4 (they reuse M1's mechanics with different content and goals), the per-patient timeline, and the per-navigator activity feed so Track A actions are visible even when they never escalate.

1 / 5

Explicitly deferred

  • Voice-agent call placement and the listen-and-summarize half of playbook 5 (needs telephony, consent handling, STT). The talk-track and manual capture ship without it.
  • NLP-based Lung-RADS / Fleischner extraction. Risk classification runs on structured fields only.
  • A configurable automation-tier engine. The POC hardcodes binary to automatic, open-clinical to assisted.
  • Self-service playbook editing and role-mapping config. Both are versioned files in the POC.
  • Cross-program enrollment linking and the insurance/coverage data source.
Open decisions worth resolving before M1
Three things are genuine choices, not defaults: the SLA window before an ordering physician's silence counts as an implicit decline in the ownership chain; the fallout-detection sensitivity (too loose and everything escalates, too tight and real concerns get missed, likely needs a short tuning pilot); and whether outcome_summary is pure navigator entry or AI-drafted-then-confirmed, which changes both build scope and the strength of the audit artifact.
