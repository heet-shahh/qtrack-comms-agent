Patient Communication Agent

2026-07-21 Status: working POC Navigator + Admin Voice: live (Retell)

A working prototype. One engine turns a clinical trigger into a tracked conversation that either finishes on its own or hands off to a navigator. It runs over text today, and as of this build, over a real voice call too. The engine is the same either way; only the channel changes.

01 The idea

Follow-up adherence is low not because the messages are badly worded, but because a trigger (a no-show, an overdue scan, a new finding) never reliably becomes a tracked action with a goal and an owner. So we built an engine, not a chatbot.

The whole model is two things and one action:

  • Workflow: a condition plus what to do about it: the goal, what to say, when to give up, and what happens next. Configurable, one per condition.
  • Task: one workflow running for one patient. It is a small state machine that carries the context and the current step.
  • Advance: the one action that moves a task forward when a timer fires or a reply arrives, and writes every step to a log.

The bet the whole thing rests on:

A single "chatbot"
→
Per-condition workflows over one shared engine
The channel is hardcoded
→
The channel is a swappable part (text now, voice now too)
Outcome lives in someone's memory
→
Every step is timestamped in a log

02 Two ways in

The people who use this are not the people who configure it, so the POC has two modes behind one login (a role switch stands in for real permissions).

Navigator (clinical)Admin (workflow management)
The everyday view for the nurse or coordinator who makes the calls. The setup and monitoring console for ops.
A plain worklist: "3 patients need a call." Each says who and why in one line, shows talking points, and has one simple form to log the call. Edit each workflow (goal, retries, what escalates, what runs next), fire test triggers, watch the queue and the log.
No jargon. No internal states, no config. All the engine detail lives here, where it belongs.
Why it matters
A clinician should never see the word "workflow" or a state name. Splitting the two means the clinical side stays calm and obvious, while the configurability lives one switch away for the people who need it.

03 The five workflows

Five conditions in the POC. Four run automatically (simple yes/no/scheduling exchanges). One is assisted (an open clinical conversation), so a navigator makes that call and the agent just preps and captures it.

#WorkflowModeWhat the agent is trying to get
1Lung-screening eligibility outreachAutomaticInterest in a free scan
2No-show / overdue chaseAutomaticA date to reschedule
3Pre-scan reminderAutomaticConfirm attendance
4General appointment reminderAutomaticConfirm attendance
5New finding (needs explaining)AssistedA navigator call, logged

The line between the two is not how serious the case is. It is whether the useful reply can be anticipated. "Does Tuesday work" has a fixed set of answers, so it is automatic. "Is this serious" cannot be scripted, so it is always assisted.

04 One conversation, start to finish

Here is the overdue-chase workflow running end to end. Step through it: the active hop lights up in the diagram. Steps 1 to 6 are the happy path; step 7 is the branch when the patient goes off-script.

→ → → → → →
Step 1 · A trigger fires

The nightly scan notices Margaret's follow-up CT is 30 days overdue with nothing booked. It creates a task from the overdue-chase workflow, with the goal stamped on: get a reschedule date.

Step 2 · Write the message

The brain writes a short, friendly message from the workflow and the patient's context. One question, with an opt-out.

Step 3 · Send it

It goes out over the patient's channel (text today) and is saved to the log.

Step 4 · The reply comes back

"Sure, how about next Monday afternoon?" The reply is logged and handed to the brain.

Step 5 · Read it against the goal

The brain answers one question: does this meet the goal, and if so what is the answer? It returns "reschedule, next Monday" with no red flags. That is a match.

Step 6 · Close and set up the next step

The task completes, the date is saved, and the next task (a pre-scan reminder before that date) is created automatically. Goal met, next goal queued.

Step 7 · The other branch

If the reply had been "why do I even need this?", the brain flags it. The agent does not answer the medical question. It hands off to a navigator (see the next section).

1 / 7
The one clever step
Reading the reply is not keyword-matching. The brain scores it against the goal and flags worry or confusion in one pass. That same step is what lets the voice version work with no change (section 06).

05 When it goes off-script

The most important safety behaviour: an automatic message must never guess at a medical question, and must never let one quietly drop. When a reply does not fit, the agent runs the same three moves every time.

→ → → →
Notice

The reply fits no expected answer, or carries worry ("no, I can't afford it"). The brain flags it. The V1 rule is simple: does not fit means escalate.

Acknowledge, do not answer

There is no script for "why do I need this," so the agent does not invent one. It warmly acknowledges the question and does not attempt an answer.

Name a specific person and time

"I'll have Sarah, your care coordinator, call you back today." A named person and a "today" beats a vague "someone will follow up."

Confirm what did resolve

If they already confirmed the appointment, the agent still confirms that, so nothing feels dropped. A call never ends mid-question.

Hand off with the question visible

The task moves to the navigator's worklist with the actual question shown and a same-day deadline attached. This is the moment automatic becomes assisted.

06 Voice, for real

The claim from day one was "the channel is just a part you swap." This build proves it. The same workflow that runs over text now runs as a real voice call, using Retell. No rewrite of the engine, the goals, or the escalation logic.

→ → → →
Pick the workflow

In the admin console, choose a workflow and a patient. The agent's instructions are built from the same workflow config that drives the text version.

Build the voice agent

The backend creates a Retell voice agent from that talk track and hands the browser a one-time call token. The Retell key stays on the server and is never exposed.

Have a real conversation

Press start and talk through your mic, playing the patient. The agent speaks, listens, and chases its one goal, just like the text flow, but out loud. No phone number needed; it runs in the browser.

Get the transcript

When the call ends, the full transcript and a recording come back.

The same brain reads it

The exact function that reads a text reply reads the voice transcript and maps it to the workflow's outcome: a match would close the task, a worry would escalate. Text and voice converge on the same finish line.

Honest status
The voice call, transcript, and outcome-reading all work today. What is not wired yet: pushing that voice outcome straight back onto the task automatically, outbound calls to a real phone (needs a number and consent handling), and swapping the rule-based brain for a model call.

07 Built, and what is next

Working now

  • Two modes: the simple clinical worklist and the admin workflow console.
  • Five workflows, four automatic and one assisted, over a text channel.
  • Editable workflows: change a goal, retries, escalation words, or the next step, and new tasks follow it.
  • The off-script handoff, the navigator worklist, per-patient history, and a full step-by-step log.
  • A real voice call (Retell) driven by a workflow, with the same brain reading the transcript.

Next

  • Post the voice-call outcome straight back onto the task, so a call completes or escalates it hands-free.
  • Outbound calls to real phones, which brings in phone numbers and call-recording consent.
  • Replace the rule-based brain with a model call (same inputs and outputs, so nothing else changes).
  • Wire real EMR and scheduling events in place of the trigger simulator.
