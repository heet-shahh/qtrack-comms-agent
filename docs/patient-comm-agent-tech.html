Technical Design & Implementation

2026-07-21 Working POC Voice: live (Retell) Companion: PRD →

How the system is built. The what and why are in the companion PRD; this document is the engine, the state machine, the channels, and the current build. The one bet everything rests on: the channel is a swappable adapter, and the engine behind it never changes.

01 Architecture

Triggers enter from the left. Everything inside the container is what we build. The dashed region is the one deliberate seam: the channel adapter, where text lives today and voice plugs in. Nothing to its left cares which channel is attached.

ComponentJob
Trigger engineTwo inputs: EMR/RIS events, and a nightly scan for time-based conditions ("overdue by N days"). Both mint tasks.
Workflow registryThe versioned configs (goal, retries, escalation, next step). Loaded onto a task at creation. Editable in the admin console.
State executorThe advance(task, event) loop. The only place state changes; writes the event log on every transition.
BrainComposes a turn and interprets a reply against the goal. Channel-independent.
Channel adapterAn interface: send a turn, receive a reply. Text stub today; the Retell voice adapter is real.
StoresTask (current state), event log (every transition), comm log (every message and reply).

02 Core objects & the state machine

Workflow (the config)

A versioned object, one per condition. It describes behaviour; it never runs.

FieldMeaning
triggerThe condition that mints a task.
tierautomatic or assisted.
goal, successOutcomeWhat the agent chases, and what counts as done.
expectedOutcomesThe closed set of replies that count as a match.
barrierSignalsWords that force an immediate escalation even inside a matched reply.
retryPolicyMax attempts, wait interval, and the channel-escalation ladder.
nextTaskOnSuccessWhat to spawn on success (for example, a pre-scan reminder).

Task (the running instance)

One workflow running for one patient. It carries the live context, the current state, attemptCount, the captured outcomeSummary, and (for assisted) the ownership and navigator fields. It is the object every log row points back to.

States

Every task moves through the same states; the transition rules differ per workflow. created → queued → in_progress → (completed | escalated). Automatic tasks close on a matched reply; the assisted task closes only when the navigator fills the capture fields (the completion gate).

03 The conversation loop

The overdue-chase workflow, end to end. Stepping lights the active hop. Steps 1 to 6 are the happy path; 7 is the off-script branch.

→ → → → → →
Step 1 · Trigger

The nightly scan finds a follow-up CT 30 days overdue with nothing booked, and creates a task from the workflow with the goal stamped on.

Step 2 · Compose

The executor asks the brain for a turn, built from the workflow script and the patient's context. State becomes in_progress, attempt 1.

Step 3 · Send

The channel adapter delivers it and writes the outbound message to the comm log.

Step 4 · Reply

The inbound reply is appended to the log and handed to advance().

Step 5 · Interpret

The brain returns a structured outcome and flags any barrier or off-script content. Here: reschedule_requested, date extracted, no flag.

Step 6 · Close and chain

State becomes completed, the outcome is written, and nextTaskOnSuccess spawns the pre-scan reminder for the captured date.

Step 7 · The fork

Had the reply been off-script, the brain flags it and the task escalates instead of completing (next section).

04 Fallout & escalation logic

The interpret step returns one of three things: a clean match, an unclear reply (retry on cadence), or a fallout / barrier (escalate now). Escalation runs a fixed three-move script before the task changes state:

  • Acknowledge, do not answer. No script exists for a clinical question, so the agent does not generate one.
  • Name a specific person and a timeframe. The patient's assigned navigator, falling back to on-call, with a same-day promise.
  • Confirm what did resolve. If the appointment was already confirmed, confirm it, so nothing feels dropped. A call never ends mid-question.

The task then moves to escalated, the assigned navigator is set, the triggering reply is attached, a structured escalation reason is written, and an SLA is applied. V1 detection is deliberately simple: a reply that does not fit the expected set escalates. A richer classifier is a fast-follow.

05 Channels & the voice adapter (Retell)

A channel is an adapter with two responsibilities: deliver a turn, and surface a reply. Text is a stub in the prototype. The voice adapter is a real integration with Retell, and it reuses the entire engine unchanged: same workflow, same goal, same interpret step.

→ → → →
1 · Build the agent from the workflow

The backend turns the workflow plus patient context into a talk track and creates a Retell LLM and agent (cached per prompt + voice so it does not leak new agents on every call).

2 · Mint a web-call token

The backend calls Retell's v2/create-web-call and returns a short-lived access_token to the browser. The Retell API key stays server-side and is never exposed to the client.

3 · Talk in the browser

The Retell Web SDK connects over WebRTC using the token. No phone number is needed. The agent speaks and listens, chasing its one goal, and the live transcript streams in.

4 · Retrieve the transcript

When the call ends the frontend polls v2/get-call for the transcript, recording, and Retell's own summary and sentiment.

5 · The same brain reads it

The exact interpret() that reads a text reply reads the patient's words from the transcript and maps them to the workflow outcome. Text and voice converge on the same finish line.

Backend surface (Express, holds the key):

EndpointDoes
GET /api/voicesLists Retell voices for the picker.

Security The key lives only in a gitignored server/.env, never in the frontend and never committed. The browser only ever receives a short-lived per-call token.

06 The brain

Two functions, one contract, channel-independent:

  • compose(workflow, patient, attempt) returns the next turn to say or send.
  • interpret(reply, workflow) returns { matched, outcome, fallout, barrier, rationale }.

In the prototype both are transparent rule-based stubs, so the behaviour is easy to read and demo. They are written to the exact input and output shape a model call will have, so swapping in a hosted model is a drop-in with no change anywhere else. The interpret stub already does double duty: it reads text replies and voice transcripts through the same code path.

07 Data & logging

Three stores. The task table is current state; the two logs are append-only history.

StoreHolds
TaskCurrent state, context, attempt count, outcome, ownership and navigator (assisted).
Event logEvery state transition: from, to, who changed it, timestamp, note. The audit trail.
Comm logEvery message and reply, patient-indexed and cross-task, so a full history is one lookup away.

The event log is what answers "how long did this sit before someone acted", regardless of whether the outcome was favourable.

08 Stack & running it

LayerChoice
FrontendReact + Vite. Two shells: navigator (clinical) and admin (workflow console).
StateA single store standing in for the backend: triggers, advance(), escalation, capture, and editable workflows.
Voice backendExpress, holds the Retell key, mints web-call tokens.
Voice clientRetell Web SDK over WebRTC in the browser.

Run both together with npm run dev:all (frontend on 5180, backend on 8787, with the frontend proxying /api). The Retell key goes in server/.env (copy server/.env.example).

09 Build status

Working now

  • Both experiences: the clinical worklist and the admin workflow console.
  • Five workflows over a text channel, with retries, the off-script handoff, and the completion gate.
  • Editable workflows that flow into the live engine, a per-patient history, and a full event log.
  • Case handoff: a navigator can reassign a task to a colleague, and the change is logged.
  • A real Retell voice call driven by a workflow, with the same interpret step reading the transcript.

Next

  • Post the voice-call outcome straight back onto the task so a call completes or escalates it hands-free.
  • Outbound calls to real phones (phone numbers, call-recording consent).
  • Swap the rule-based brain for a hosted model (same contract, no other change).
  • Wire real EMR and scheduling events in place of the trigger simulator.
